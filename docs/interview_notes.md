# 面试讲解稿与常见问题（v0.2）

本文描述当前代码，不再把已实现的 LangGraph、SQLite、人工审核列为未来计划。详细架构见 [architecture.md](architecture.md)，页面学习步骤见 [learning_path.md](learning_path.md)。

## 1. 如何介绍项目

这是一个面向电商客服的工程化工作流项目，前端 Vue 3 + TypeScript，后端 FastAPI，LangGraph 编排订单查询、政策问答、订单号补充与审核建单。SQLite 保存业务数据、执行检查点和审计记录。当前使用测试业务数据，支持单实例低并发验证，不宣称真实企业上线效果。

## 2. LangGraph 已经用在哪里

`app.py → WorkflowService.start() → build_graph()` 是默认入口。图显式注册 intent、clarify、order、policy、review、ticket、response 节点及条件边；`SqliteSaver` 保存检查点，`interrupt()` 等待补充/审核，`Command(resume=...)` 恢复同一个 thread_id。`CustomerSupportAgent` 类保留为兼容入口，不表示编排还未迁移。

## 3. 为什么不只用 if/else

单次同步查询可以用 if/else，但订单号补充、跨请求审核和服务实例重建后的恢复需要持久化执行状态。图负责状态流转；运行登记负责请求身份、输入指纹和业务访问范围，两者不等同于普通执行日志。

## 4. 模型与业务工具如何分工

模型可以做受白名单校验的意图分类和基于业务证据的回复生成。默认分类规则可在没有模型的情况下运行；是否调用模型由实际环境配置决定。

当前业务工具由显式图节点调用，默认 `ScopedTools` 直接访问本地业务库，不是自主模型随意选择工具或通过旧 HTTP Mock 适配器执行。服务端始终校验身份、订单归属和审核角色。

## 5. 人工审核是否等于自动转真人聊天

不是。当前实现的是待审核队列及“通过/拒绝后继续工作流”，没有真人坐席聊天系统，也没有任意跨会话长期记忆。补充订单号和审核可恢复同一个 run，不能直接称为完整多轮对话平台。

## 6. 故障、重试与幂等怎么讲

只读节点有有限重试；模型回复失败保留模板，模型分类失败回退规则。模型失败不会自动进入一个所谓的三级转人工链路，审核由业务路径触发。

工单写成功后、检查点保存前故障，恢复可能重放 ticket 节点。因此业务库还要使用唯一幂等键、事务和参数冲突检查，避免重复记录。请求侧还检查 request_id 与输入指纹，不允许同一编号复用到不同请求。

## 7. RAG 到了什么程度

当前是中文字符 1-4 gram TF-IDF 基线，配合查询扩展、Top-K 和来源片段。没有 Dense/混合检索或重排序的已验证效果，也没有 SFT/LoRA 训练成果。不要把另一个内部知识库项目的能力搬到这里。

## 8. 如何说明测试和效果

仓库自动化测试主要验证权限、工作流状态、审核拒绝、恢复、幂等和模型回退；模型请求在测试中隔离，不消耗真实额度。以实际测试输出及 CI 结果为准。功能测试通过不代表意图识别准确率、客户满意度或生产可用性已经达标。

如果使用个人开发集报告准确率，应同时说明样例数、标注方式、规则/模型开关、失败样例和是否独立测试；不凭模型名称或配置声称已完成真实联调。

## 9. 真正的下一步

- 固定开发集和独立测试集，测意图、检索、回复依据、延迟和成本。
- 接真实身份和业务适配器，验证授权、人工流程与外部幂等。
- 多实例部署时一起设计检查点、分布式锁、任务调度和状态对账。

面试时区分“代码已实现”“本地已验证”“尚未接入生产”，不要把计划说成成果。
